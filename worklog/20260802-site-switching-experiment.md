# 会話途中の Tableau サイト切替(実験)

日付: 20260802
ブランチ: claude/site-switching-experiment

## 背景

1つの MCP コネクタのまま、会話の途中でユーザーのプロンプト起点で接続先サイトを
切り替えたい。制約は2つ: MCP セッション層はステートレスを維持する(サーバーサイドの
セッションストアで「現在サイト」を持たない)、切替は既定で無効(現行挙動を変えない)。

当初案は MCP 仕様の step-up authorization(サイトをスコープ化し、403 +
`insufficient_scope` チャレンジで再認可させる)だったが、実装前の実測で
Claude Code が 403 チャレンジに反応しないことを確認した
(verification/site-switching/FINDINGS.md 項1)。一方、401 `invalid_token` への
サイレントリフレッシュ + 元呼び出しの自動再試行は完全に動く(同 項2)。
そこで切替トリガーを 401 経路に置いた。

## 変更内容

5コミット。前3つは切替に依存せず単独で成立する。

1. `6e013a35` — トークン検証失敗の 401 に `WWW-Authenticate` ヘッダを付与(RFC 6750)。
   従来は JSON ボディのみで、サイレントリフレッシュの起動条件を欠く可能性があった
2. `c815dbe2` — JWE アクセストークンに `jti` を追加し、`EmbeddedOAuthProvider` に
   TTL 付き失効セット(既存 `ExpiringMap`)を新設。トークン単位の失効を可能にする。
   スキーマは optional で既存発行トークンを壊さない
3. `2f7816b1` — サイトスコープ `tableau:site:<contentUrl>` のモデル化(記録のみ)。
   PRM の `scopes_supported` には載せず、スコープ検査でも強制しない
4. `1d57024c` — `POST /oauth2/switchSite` エンドポイント。グラント(RefreshTokenData)の
   Tableau トークンを切替先サイト指定で即時交換し、成功時のみグラントを書き換えて
   現アクセストークンの `jti` を失効させる。次のリクエストが 401 → クライアントが
   無音リフレッシュ → 既存のリフレッシュ経路が新サイトのトークンを発行する
5. `1d2b8b72` — ツール3種 `switch-site` / `get-current-site` / `list-sites`。
   新設の `OAUTH_SWITCHABLE_SITES`(カンマ区切り allowlist)が未設定なら
   ルートもツールも登録されず、既定の挙動は現行と完全一致

## 設計判断

- **403 チャレンジ(仕様準拠経路)を主線にしない。** クライアント実測が根拠。
  サイトスコープの記録と拡張点(authorize のスコープ検証例外・403 チャレンジ生成・
  `target_site` 反映の3箇所)は残してあり、対応クライアントが現れたら別 PR で足せる
- **予約方式(切替をリフレッシュ時まで遅延)は不採用。** リフレッシュ処理には
  「Tableau 交換失敗時に旧トークンを再利用して成功させる」フォールバックがあり、
  予約方式ではそこに落ちると切替失敗が誰にも届かない。即時交換ならツールが
  同期的にエラーを返せる。副次効果としてリフレッシュハンドラは無変更で済む
- **ツールから provider の Map を直接触らず、自己 POST(`/oauth2/switchSite`)。**
  既存 `revoke-access-token` と同じパターンで、認可サーバーの境界を保つ
- **allowlist は overridableConfig(MCP サイト設定)に載せない。** サイト A の管理者が
  サイト B への切替可否を決める権限逆転が起きるうえ、サイト設定キャッシュのキーが
  サイト依存のため循環する。デプロイ管理者の環境変数に閉じた
- **複数コネクタ並置・サーバーサイドセッションストアは前段の検討で不採用**(制約に反する)

## 検証

- 単体: `npm test` 2875/2876 pass(失敗1件は main にも存在する FeatureGate の
  パス解決問題で無関係)。eslint / tsc クリーン
- 統合: `npm run test:oauth:embedded` 95/95 pass。切替→401(`WWW-Authenticate` 付き)→
  リフレッシュ→ Tableau 交換が切替先 `site_namespace` で呼ばれる一連、交換失敗時に
  グラントが不変で旧サイトのまま動き続けること、機能無効時のルート不在を含む
- 実測: クライアント挙動(403 不発・401 サイレントリフレッシュ)は実 Claude Code で
  確定済み。**Tableau 側の切替成功経路は未実測** — 埋め込み認可サーバーモード自体が
  Tableau Cloud で拒否されるため(verification/site-switching/FINDINGS.md 項4)、
  Tableau Server 2025.3+ かつ複数サイトの環境が要る

## 残課題

- FINDINGS 記載の未実測4点。特に「同一 Tableau リフレッシュトークンで別サイトの
  `site_namespace` が通るか」は機能成立の前提であり、通らない場合は REST
  `switchSite` フォールバック(SDK へのエンドポイント追加が必要)を検討する
- claude.ai / Claude Desktop リモートコネクタの 401 リフレッシュ挙動は未計測(CLI のみ)
- 切替直後の並行リクエストとリフレッシュトークンローテーションの競合。
  グレース期間の導入は切替と独立の堅牢化として別件
- セッション管理有効時、切替後もツール一覧が initialize 時のサイト設定のまま
  (ステートレス構成では起きない)。運用制約として文書化どまり
- upstream PR 化はコミット1〜3が候補(切替本体はフォーク維持が現実的)。
  出す場合は本ファイルを要約して PR 本文にする
